Spec-driven development

Le prompt ne suffit pas

Ajoute la fusion de deux tickets.

  • Que deviennent les commentaires du ticket fusionné ?
  • Peut-on fusionner un ticket fermé ? Les tickets de deux clients différents ?
  • Quelle priorité garde le ticket conservé ?

L'agent ne pose pas toujours ces questions : il comble les trous avec des choix plausibles.

Le principe

Le spec-driven development fait écrire une spécification validée avant tout code, puis la donne à l'agent comme guide.

flowchart LR
    S[Spécifier] --> V[Valider]
    V --> P[Planifier]
    P --> I[Implémenter]
    I --> C[Vérifier contre la spec]
    C -- écart --> I

On relit une spécification de 20 lignes plus facilement qu'un diff de 300.

Une spécification

# Fusionner deux tickets

## Contexte
Un client ouvre parfois deux tickets pour le même problème.

## Règles
- Le ticket absorbé est fermé, ses commentaires passent sur le ticket conservé.
- On ne fusionne pas un ticket fermé, ni les tickets de deux clients différents.
- Le ticket conservé prend la priorité la plus haute des deux.

## Critères d'acceptation
- Étant donné deux tickets ouverts du même client,
  quand je fusionne #12 dans #8,
  alors #12 est fermé et ses commentaires apparaissent sur #8.

## Hors périmètre
- Annuler une fusion.

Spécification et tests

  • Les règles disent à l'agent ce qu'il ne doit pas inventer.
  • Les critères d'acceptation se traduisent en tests.
  • Le hors périmètre l'empêche d'en faire trop.

La spécification est un guide ; les tests qui en découlent sont des capteurs.

Des outils pour standardiser

Plusieurs projets outillent la démarche avec des commandes à lancer dans l'agent :

  • GitHub Spec Kit, maintenu par GitHub
  • OpenSpec, pensé pour les projets existants
  • BMAD-METHOD, qui couvre tout le cycle produit

Ils produisent des fichiers Markdown versionnés avec le code : spécification, plan, tâches.

GitHub Spec Kit

uv tool install specify-cli
specify init helpdesk --integration copilot
/speckit-constitutionprincipes du projet, une fois pour toutes
/speckit-specifyspécification de la fonctionnalité
/speckit-planplan technique
/speckit-tasksdécoupage en tâches
/speckit-implementimplémentation
/speckit-convergevérification de l'écart avec la spécification, à répéter avec implement

BMAD-METHOD

npx bmad-method install
  • une boucle en quatre temps : clarifier, planifier, construire et vérifier, apprendre et ajuster
  • des expertises mobilisées selon le besoin : produit, architecture, UX, développement, tests
  • une planification plus ou moins poussée selon la taille du changement

Version stable 6.12.4 (octobre 2026). La v7 est en préversion, avec des changements cassants d'une mise à jour à l'autre.

Dans ce cours

Ces outils sont présentés, pas appliqués :

  • ils évoluent trop vite : BMAD a renommé et retiré des skills en 6.11, introduit des changements cassants en 6.12, et prépare une v7
  • ils outillent la spécification, ce cours outille la vérification

Retenez l'idée : une spécification écrite, validée, avec des critères vérifiables, avant le code.
