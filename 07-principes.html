SOLID

Responsabilité unique

Créer un ticket depuis un contrôleur qui fait tout :

  • lire et valider le formulaire
  • calculer la priorité selon l'offre du client
  • enregistrer le ticket
  • notifier le client
  • choisir la page de redirection

Cinq raisons de changer pour une seule classe. La règle de priorité doit être recopiée dans l'API et dans toute nouvelle fonctionnalité.

Responsabilité unique

final class TicketOpener
{
    public function __construct(
        private PriorityPolicy $priorityPolicy,
        private EntityManagerInterface $em,
        private Notifier $notifier,
    ) {
    }

    public function open(Customer $customer, string $title, Priority $requested): Ticket
    {
        $priority = $this->priorityPolicy->for($customer, $requested);
        $ticket = new Ticket($customer, $title, $priority);
        $this->em->persist($ticket);
        $this->em->flush();
        $this->notifier->ticketOpened($ticket);

        return $ticket;
    }
}

Le contrôleur et l'API appellent le même service : la règle n'existe qu'à un endroit.

Ouvert/fermé

#[AutoconfigureTag]
interface NotificationChannel
{
    public function send(Ticket $ticket, string $event): void;
}

final class Notifier
{
    /** @param iterable<NotificationChannel> $channels */
    public function __construct(#[AutowireIterator(NotificationChannel::class)] private iterable $channels)
    {
    }

    public function notify(Ticket $ticket, string $event): void
    {
        foreach ($this->channels as $channel) {
            $channel->send($ticket, $event);
        }
    }
}

Ajouter les SMS, c'est ajouter une classe qui implémente NotificationChannel, sans toucher à Notifier.

Liskov et ségrégation des interfaces

Substitution de Liskov

Une sous-classe qui lève une exception là où la classe parente fonctionne casse le code qui l'utilise.

Un ArchivedTicket extends Ticket dont setAssignee() lève une exception viole le principe : l'état « archivé » est un statut, pas un sous-type.

Ségrégation des interfaces

Une classe ne doit pas dépendre de méthodes qu'elle n'utilise pas.

La commande nocturne n'a besoin que de findResolvedBefore() : elle peut dépendre d'une petite interface plutôt que de tout le dépôt.

Inversion des dépendances

use Psr\Clock\ClockInterface;

final class SlaCalculator
{
    public function __construct(private ClockInterface $clock)
    {
    }

    public function isLate(Ticket $ticket): bool
    {
        return $this->dueDate($ticket) < $this->clock->now();
    }
}

Avec new \DateTime(), le retard dépend de l'heure réelle : impossible de tester un ticket créé un vendredi soir. Avec ClockInterface, un test fournit l'heure qu'il veut.

KISS

Keep It Simple, Stupid : la solution la plus simple qui répond au besoin.

  • pas d'abstraction tant qu'il n'y a qu'une implémentation
  • pas de configuration pour un cas qui n'existe pas encore (YAGNI : You Aren't Gonna Need It)
  • le code le plus simple est le plus facile à relire, pour vous comme pour l'agent

Un agent a tendance à en faire trop : interfaces, options, cas limites que personne n'a demandés. Chaque ligne en trop est une ligne à relire.

DRY

“Every piece of knowledge must have a single, unambiguous, authoritative representation within a system.”

- Andy Hunt et Dave Thomas, The Pragmatic Programmer
  • DRY parle de connaissance : une règle métier, un format, une constante
  • deux bouts de code qui se ressemblent par hasard ne sont pas une duplication
  • une règle recopiée trois fois finit par diverger : une copie est corrigée, les autres non

Un agent cherche rarement si une fonction existe déjà : il la réécrit.

Des principes, pas des règles

Les principes guident la conception, mais aucun outil ne les vérifie entièrement.

  • Deptrac vérifie une partie de la séparation des responsabilités : qui a le droit de dépendre de qui
  • PHPStan vérifie les types, et donc une partie des contrats
  • le reste passe par la relecture et par les guides donnés à l'agent

Un principe écrit dans AGENTS.md est un guide ; une règle Deptrac est un capteur.
